# OMM 발표 메시지 정리

관련 문서: [demo-scenarios.md](demo-scenarios.md) · [presentation-outline.md](presentation-outline.md) ·
[mentoring-demo.md](mentoring-demo.md)

이 문서는 멘토링 두 번에서 나온 방향을 하나로 합친 발표 메시지입니다. 기능을 나열하지 않고
**왜(Why) · 누구에게(Who) · 무엇을(What)** 순서로 말합니다.

작성 원칙:

- 모든 명령과 메뉴 이름은 현재 코드(`src/`, `web-ui/src/`, `docs/commands.json`)에서 확인했습니다.
- 아직 사람이 실제로 해 보지 않은 것은 **미검증**, 코드가 아직 없는 것은 **구현 예정**이라고 적습니다.
- 사용자 평가 결과·절약 수치처럼 아직 모으지 않은 숫자는 만들지 않습니다.
- 클러스터(`omm cluster`)는 아직 `main`에 들어오지 않은 브랜치(`docs/exo-cluster-plan`)의 기능입니다.
  발표에서는 반드시 "개발 중(브랜치), 실측 기록 있음"이라고 말합니다.

## 1. 한 줄 메시지

> **OMM은 GPU 서버 없이, 이미 가진 PC·노트북·Mac mini로 내 업무에 맞는 로컬 AI를
> 쉽고 안전하게 세우는 오픈소스 플랫폼입니다.**

짧은 버전(슬라이드 표지용): **"서버 없이, 내 컴퓨터로, 내 자료를 밖에 보내지 않는 AI."**

두 멘토링을 어떻게 합쳤나:

| 멘토링 | 핵심 단어 | 합친 메시지에서 |
|---|---|---|
| 1차 | 내 컴퓨터·업무에 맞는 Local AI, 쉽고 빠르게, 분석→추천→설치→실행→RAG→운영 | "내 업무에 맞는 로컬 AI를 쉽고 안전하게 세우는" |
| 2차 | GPU 서버 없이, 유휴 Mac mini·노트북·PC를 묶어, 저비용, 단계적 확장 | "GPU 서버 없이, 이미 가진 PC·노트북·Mac mini로" |

한 대에서 시작(1차 흐름)하고, 부족하면 여러 대를 묶는다(2차 흐름). 이것이 "단계적 확장" 이야기입니다.

## 2. Why · Who · What

### Why — 왜 필요한가

- 생성형 AI를 쓰고 싶어도 **내부 자료를 외부 AI 서비스에 보낼 수 없는** 곳이 많습니다.
- 로컬 AI를 직접 세우려면 실행기 설치, 모델 고르기, 메모리 계산, 연결 설정을 각자 알아서 해야 합니다.
  처음 하는 사람은 "내 PC에 어떤 모델이 맞는지"부터 막힙니다.
- 큰 모델을 돌리려면 보통 GPU 서버를 사야 한다고 생각합니다. 하지만 사무실에는 이미 쓰지 않는
  시간이 많은 PC와 Mac이 있습니다.

### Who — 누구를 위한 것인가

1. **처음 써 보는 개인·학생:** 명령줄이 낯설고, 모델 이름과 양자화(Q4 같은 표기)를 모릅니다.
2. **AI 담당자가 없는 중소기업:** 사람을 새로 뽑거나 서버를 사기 어렵습니다.
3. **내부 자료를 밖으로 못 보내는 조직:** 문서 질문과 코딩 도우미를 로컬에서만 쓰고 싶습니다.

### What — OMM이 하는 일

한 대에서:

1. 하드웨어(메모리·GPU)를 읽고 **맞는 모델을 근거와 함께 추천**합니다 (`omm recommend`, 웹 **추천**).
2. 버튼 한 번 확인으로 **실행 앱 확인 → 앱 안전 검사 → 로컬 서버 확인 → 모델 파일 준비 → 실행 앱 연결 →
   실제 응답 확인** 6단계를 이어서 하고 채팅을 엽니다 (웹 **이 모델로 대화 시작** / **대화 준비하고 시작**).
   현재 Ollama와 LM Studio만 지원합니다.
3. 모델 파일을 한 곳(`OMM_HOME`)에 두고 실행 앱마다 **복사 대신 링크**해서 중복 저장을 줄입니다.
4. **내 문서**에 PDF·TXT·Markdown·HTML·HWPX를 등록하고 질문하면, 답과 함께 **출처 구간(쪽 번호)**을 보여 줍니다.
   검색은 이 컴퓨터 안에서만 하고(네트워크 호출 없음), 답은 사용자가 고른 로컬 모델이 만듭니다.
5. Claude Code·Codex CLI·pi 같은 코딩 도우미를 **로컬 Ollama 모델로 연결**하고, 원래 설정으로 되돌립니다
   (`omm agent local|status|cloud`).

여러 대에서 (개발 중, 브랜치):

6. Thunderbolt로 이은 Mac 여러 대를 `omm cluster init` / `join`으로 **하나의 AI 서버처럼 묶고**, 직원은
   토큰이 있어야만 들어오는 게이트웨이로 접속합니다. exo를 실행 백엔드로 씁니다.

## 3. 네 가지 가치

| 가치 | 한 문장 | 근거(현재 코드·기록) |
|---|---|---|
| **쉬움** | 모델 이름을 몰라도, 추천을 보고 버튼 한 번 확인으로 첫 대화까지 간다 | `web-ui/src/main.jsx` 버튼, `src/omm/web/task_flow.py`의 6단계 |
| **안전·사생활** | 문서와 대화는 내 컴퓨터에 남고, 관리 화면은 이 컴퓨터 안(127.0.0.1)에서만 열린다 | `src/omm/web/server.py` 바인딩, `src/omm/documents.py` "No network calls", 업로드는 모두 동의제(`PRIVACY.md`) |
| **저비용** | 새 GPU 서버 대신 이미 있는 기기를 쓰고, 같은 모델 파일을 두 번 받지 않는다 | 링크 공유(`omm scan`의 "GB saved by linking instead of copying"), 클러스터 실측(아래) |
| **단계적 확장** | 한 대 → 코딩 도우미 연결 → 사내 문서 → 여러 대 묶기로 필요한 만큼 키운다 | `omm agent`, **내 문서**, `omm cluster`(브랜치) |

클러스터 실측 기록(브랜치 `docs/exo-cluster-plan`의 `docs/superpowers/specs/2026-10-22-exo-cluster-spike-findings.md`, 2026-10-24):

- Mac mini 3대를 Thunderbolt 케이블 3개(삼각형)로 잇고 `mlx-community/Qwen3.5-122B-A10B-8bit`(121.7 GiB)를
  Pipeline 방식으로 3대에 나눠 올림.
- 게이트웨이: 토큰 없으면 401, 올바른 토큰은 스트리밍 200. 첫 글자까지 1.5초, 약 초당 20토큰.
  노트북의 Claude Code가 파일 읽기 작업을 끝까지 함.
- 한 대(측정한 node3은 64 GiB)로는 메모리가 모자라 이 모델을 올릴 수 없습니다. **같은 질문을 한 대와
  여러 대로 비교한 속도 실측은 아직 없습니다(미검증).** 나머지 두 대의 메모리 용량은 기록에 없어 확인이 필요합니다.

## 4. 문제 → 해결 흐름 (발표 뼈대)

멘토 제안 순서: 문제 → 기존 방식 한계 → 해결 → 동작 → 기술 → 효과 → 확장.

1. **문제:** 내부 자료 때문에 클라우드 AI를 못 쓰고, 로컬 AI는 세우기 어렵고, GPU 서버는 비싸다.
2. **기존 방식의 한계:** 실행기(Ollama, LM Studio 등)는 "모델을 돌리는 것"까지 합니다. 어떤 모델이 내 PC에
   맞는지, 실제로 답을 하는지, 실행기마다 같은 파일을 또 받는 문제, 문서 질문·코딩 도우미 연결은 각자 따로 해야 합니다.
   여러 대를 묶는 exo는 강력하지만 방화벽·인증·네트워크 설정은 사용자 몫입니다.
3. **해결:** OMM이 그 사이를 잇습니다. 분석·추천 → 설치·연결 → 실제 응답 확인 → 대화·문서·코딩 도우미 → (여러 대)묶기.
4. **동작:** 시연 A·B·C ([demo-scenarios.md](demo-scenarios.md)).
5. **기술:** 하드웨어 분석과 추천 근거 표시, 서명된 추천 카탈로그, 링크 기반 모델 허브, 6단계 작업 흐름,
   로컬 어휘 검색 기반 문서 질문(SQLite, `local_lexical_v1`), 하네스 설정 백업·복원, (브랜치) exo + pf 방화벽 + 토큰 게이트웨이.
6. **효과:** 첫 대화까지 걸리는 단계 감소, 외부 전송 없는 문서 질문, 중복 저장 감소, 한 대로 못 돌리는 모델을 기존 기기로 실행.
   **사용자 평가 수치는 아직 없습니다.** 효과는 "무엇이 가능해졌는가"로 말하고, 숫자는 실측한 것만 씁니다.
7. **확장:** 클러스터 정식 병합(#503, #508), 클러스터용 문서 질문 MCP(#504, 구현 예정), Windows·Linux 실사용 검증.

비교에서 말할 것(정직한 위치):

- OMM은 **실행기를 대체하지 않습니다.** Ollama·LM Studio·exo 위에서 "고르기·연결·확인·운영"을 맡습니다.
  그래서 "Ollama보다 빠르다" 같은 말은 하지 않습니다.
- 문서 질문 품질은 AnythingLLM 같은 벡터 검색 기반 도구보다 단순합니다(현재는 단어 검색). 대신 추가 서버·임베딩 모델 없이 동작합니다.
- 여러 기기 묶기는 exo가 해 주는 일이고, OMM은 그 위에 **설치·방화벽·토큰·상태 점검·되돌리기**를 얹습니다.

## 6. 예상 심사 질문과 답 (초안)

답은 "할 수 있는 것 / 아직 아닌 것"을 같이 말합니다.

1. **Q. Ollama나 LM Studio만 쓰면 되지 않나요?**
   A. 실행은 그걸로 됩니다. OMM은 그 앞뒤를 맡습니다. 내 PC에 맞는 모델 추천, 실제 응답 확인까지 묶은 6단계 준비,
   실행 앱 사이 파일 공유, 문서 질문, 코딩 도우미 연결·복원입니다. 실행기를 바꾸지 않아도 됩니다.
2. **Q. 추천은 얼마나 정확한가요?**
   A. 정확도 퍼센트는 말하지 않습니다. 추천 화면은 근거를 나눠 보여 줍니다(번들 규칙, 서명된 카탈로그, 이 PC 속도 보정).
   근거가 부족하면 "실측 근거 부족"으로 표시합니다. 정확도를 따로 검증한 결과는 아직 없습니다.
3. **Q. 정말 외부로 아무것도 안 나가나요?**
   A. 문서 검색은 네트워크 호출이 없는 코드(`src/omm/documents.py`)이고, 관리 화면은 127.0.0.1에서만 열립니다.
   인터넷을 쓰는 때는 모델·추천 자료를 받을 때와 사용자가 누른 확인 버튼(연결 상태 확인 등)입니다.
   사용 통계·오류 보고·벤치마크 업로드는 사용자가 켜야만 동작합니다. 시연에서는 모델을 받은 뒤 Wi-Fi를 끄고 질문해서 보여 줄 계획입니다(녹화 전 확인 필요).
4. **Q. 코딩 도우미를 로컬로 바꾸면 모든 요청이 로컬로 가나요?**
   A. OMM이 바꾸는 것은 사용자 설정 파일의 연결 주소입니다. 프로젝트·조직·환경 변수 설정이 이걸 덮을 수 있어서,
   민감한 자료를 보내기 전에 도우미 안에서 실제 모델·서버를 확인하라고 안내합니다. 도구 호출이 끝까지 잘 되는지는
   로컬 모델 기준으로 아직 확인하지 않았습니다(미검증).
5. **Q. 왜 Qwen 계열인가요?**
   A. 2차 멘토링에서 범위를 Ollama + Qwen 계열 + 에이전트로 좁혔습니다. 크기가 다양하고 도구 호출을 지원하는 모델이 있으며,
   클러스터 실측도 Qwen3.5 모델로 했습니다. OMM 자체는 특정 모델에 묶여 있지 않습니다.
6. **Q. 클러스터는 지금 쓸 수 있나요?**
   A. 브랜치에서 개발 중이고 아직 `main`에 병합되지 않았습니다. Mac 3대 실측 기록은 있습니다. RDMA 켬/끔 속도 비교와
   세 대 모두에서의 `leave` 확인은 남아 있습니다(#508).
7. **Q. 왜 Mac만 묶나요? Windows PC는요?**
   A. 백엔드인 exo의 macOS 앱과 Thunderbolt RDMA를 쓰기 때문입니다. Windows·Linux 노드는 이번 설계의 목표가 아닙니다.
   직원 PC는 어느 OS든 게이트웨이에 접속할 수 있게 설계했습니다(실측은 Mac 노트북에서만).
8. **Q. 여러 대로 묶으면 더 빠른가요?**
   A. 목적은 속도가 아니라 **한 대에 안 들어가는 큰 모델**을 돌리는 것입니다. 3대에서 122B 모델이 초당 약 20토큰으로
   나왔다는 기록이 있지만, 한 대와 같은 조건 비교는 아직 없습니다.
9. **Q. 큰 모델 첫 준비가 오래 걸리지 않나요?**
   A. 맞습니다. 실측에서 각 Mac이 전체 모델(약 130.7GB)을 받아 첫 준비에 약 85분이 걸렸고, `omm cluster model`은 60분
   제한에 걸려 실패로 보였습니다. 알려진 문제로 기록했습니다(#508). 시연은 미리 받아 둔 상태에서 합니다.
10. **Q. 사내망에 열면 보안은요?**
    A. exo API는 원래 인증 없이 열립니다. OMM은 pf 방화벽으로 exo 포트를 Thunderbolt와 자기 컴퓨터에서만 받게 하고,
    게이트웨이(52440)만 토큰을 확인한 뒤 열어 둡니다. 실측 포트 스캔에서 exo 포트는 닫혀 있었습니다. 다만 v1 게이트웨이는
    TLS가 없는 평문 HTTP라서 사내망 도청 위험이 남아 있습니다(설계 문서의 "남은 위험").
11. **Q. 문서 질문은 어떤 방식인가요? 벡터 검색인가요?**
    A. 아닙니다. 지금은 단어(한국어는 두 글자 단위) 검색으로 근거 구간을 찾고, 그 구간을 로컬 모델에 넘깁니다.
    임베딩 모델이 필요 없다는 장점과, 뜻이 같은 다른 단어는 못 찾는 한계가 있습니다.
12. **Q. 어떤 문서를 넣을 수 있나요?**
    A. 텍스트 PDF, TXT, Markdown, HTML, HWPX입니다. 파일당 6 MiB, PDF는 100쪽, 문서 100개까지입니다.
    스캔 PDF(OCR)와 HWP(한글 97 형식)는 아직 안 됩니다.
13. **Q. 출처가 나오면 답이 맞다는 뜻인가요?**
    A. 아닙니다. 화면에도 "출처 번호가 있어도 답변의 정확도를 보장하지 않는다"고 씁니다. 출처 구간을 직접 확인하게 하는 것이 목적입니다.
14. **Q. "실행 확인"이 통과하면 좋은 모델인가요?**
    A. 짧은 고정 질문에 실제 글이 생성되는지만 봅니다. 답의 품질은 따로 평가합니다(`omm benchmark`, `omm evaluate`).
15. **Q. 저장 공간은 얼마나 아끼나요?**
    A. 같은 파일을 실행 앱마다 복사하지 않고 링크합니다. 절약량은 PC마다 다르고 `omm scan`과 웹 **파일·설정**이
    그 PC 기록을 보여 줍니다. 여러 사용자에게서 모은 수치는 없습니다.
16. **Q. 실제 사용자 평가는 했나요?**
    A. 아직 없습니다. 평가 양식([mentoring-demo.md](mentoring-demo.md) 3번)은 있고, 해 본 결과만 자료에 넣겠습니다.
17. **Q. 고등학생 세 명이 이걸 유지보수할 수 있나요?**
    A. 자동 테스트를 Linux·macOS·Windows에서 돌리고(`.github/workflows/ci.yml`), 모든 병합에 팀원 리뷰를 받고,
    서명 태그로 릴리스합니다. 클러스터처럼 큰 기능은 설계·실측 문서를 먼저 남깁니다.
18. **Q. 오픈소스로서 기여한 부분은?**
    A. 결과물 전체를 공개 저장소로 운영하고, 사용자가 동의한 벤치마크로 추천 자료를 개선하는 구조(`omm contribute`)가 있습니다.
    exo처럼 다른 오픈소스 위에 쌓을 때는 그 동작을 실측해 문서로 남겼습니다. 외부 프로젝트 upstream 기여 기록은 이 문서에서 확인하지 않았습니다.
19. **Q. 설치가 정말 쉬운가요? 명령줄을 써야 하잖아요.**
    A. 설치는 명령 한 줄(PowerShell 또는 터미널)이고, Python·git이 없으면 설치 스크립트가 가능한 범위에서 자동 설치합니다.
    그 뒤로는 웹 화면에서 합니다. 깨끗한 컴퓨터에서 사람이 직접 해 본 기록은 아직 없습니다(미검증).
20. **Q. 메모리가 부족한 PC에서 큰 모델을 고르면요?**
    A. 설치 전에 메모리 적합성을 계산하고(`omm fit`), 새로 불러오기 전 여유 메모리를 확인합니다. 다른 앱이 이미 올린 모델을
    OMM이 몰래 내리지 않습니다. 대신 멈추고 이유를 보여 줍니다.
21. **Q. 클라우드 API보다 싼가요?**
    A. 기존 기기를 쓰면 새 하드웨어 비용은 없지만, 전기·관리 시간·모델 품질 차이가 있습니다. 비용 비교 실측은 하지 않았습니다.
    "자료를 밖에 보낼 수 없는 경우의 선택지"로 말하는 것이 정확합니다.
22. **Q. 로컬 모델 품질이 클라우드 모델만 하나요?**
    A. 대부분 그렇지 않습니다. 그래서 작은 작업(문서 질문, 코드 읽기)부터 로컬로 하고, 큰 모델이 필요하면 여러 대 묶기로 키우는 흐름을 제안합니다.
23. **Q. 다른 앱 설정을 바꾸면 위험하지 않나요?**
    A. 바꾸기 전에 원래 파일을 `OMM_HOME/agent-connections/`에 백업하고, `omm agent cloud`로 되돌립니다.
    사용자가 중간에 연결 설정을 직접 바꿨다면 덮어쓰지 않고 멈춥니다.
24. **Q. 모델 파일이 진짜인지 어떻게 아나요?**
    A. 추천 카탈로그는 서명 검증을 요구할 수 있고(`omm setting catalog-trust`), 설치는 해시·안전 검사를 거칩니다.
    모델 설명은 출처와 검토 날짜를 함께 보여 주고, OMM이 품질을 평가하지 않은 값은 비워 둡니다.

## 7. 약점과 보완

| 약점 | 왜 문제인가 | 보완(지금 할 일) |
|---|---|---|
| 실사용 확인 기록이 거의 없음(상태표 대부분 미검증) | 심사위원이 "진짜 되나"를 의심 | 시연 A·B를 실제 실행기로 녹화하고, 녹화 날짜·OS·버전을 상태표에 기록 |
| 사용자 평가 수치 없음 | 효과를 숫자로 못 말함 | 발표 전 최소 몇 명이라도 3번 양식으로 기록, 없으면 "없다"고 말함 |
| 클러스터가 미병합 브랜치 | 심사 대상 버전에 없을 수 있음 | "개발 중"을 명확히 표시, 시연 C는 녹화 영상 + 실측 문서로 보여 줌 |
| 한 대 vs 여러 대 비교 실측 없음 | 멘토가 요청한 비교 장면이 비어 있음 | "한 대는 메모리 부족으로 올릴 수 없음"을 화면으로 보여 주고, 같은 모델 크기 비교는 측정 후 추가 |
| 문서 질문이 단어 검색 | 뜻이 같은 다른 표현을 못 찾음 | 시연 질문을 문서 단어가 들어가게 준비, 한계를 먼저 말함 |
| 코딩 도우미의 로컬 도구 호출 미검증 | 시연 B 후반부가 실패할 수 있음 | 녹화 전 리허설, 실패 시 `status` 화면과 복원까지만 보여 줌 |
| 대화 준비는 Ollama·LM Studio만 | 다른 실행기 사용자 질문 | 지원 범위를 슬라이드에 명시 |
| Windows·Linux 실사용 미검증 | "모든 OS 지원"을 말할 수 없음 | 시연 OS를 하나로 고정하고, 다른 OS는 자동 테스트 범위만 말함 |
| 게이트웨이 평문 HTTP | 보안 질문에 약함 | 설계 문서의 남은 위험으로 먼저 공개, 후속 과제로 제시 |
| 기능이 너무 많아 메시지가 흐려짐 | 멘토 1·2차 공통 지적 | 발표는 시연 세 개와 네 가지 가치만, 나머지 명령은 부록 |
