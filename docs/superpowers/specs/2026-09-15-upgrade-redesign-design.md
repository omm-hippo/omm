# `omm upgrade` 재설계 — 설계

날짜: 2026-09-15
상태: 초안 (사용자 리뷰 대기)
관련 이슈: (이 스펙 승인 후 생성)

## 배경

`omm upgrade`는 지금 "설치된 모델과 같은 파일명을 소스에서 다시 조회해, 바이트가 바뀌었으면
재다운로드"만 한다 (`cli.py:_update_one`). 실전에서 거의 안 쓰인다 — HF에 올라간 GGUF는 같은
파일명으로 바이트가 바뀌는 일이 드물기 때문이다(재양자화 수정, chat template 수정 등 예외적
경우 제외). 게다가 이 "재다운로드" 자체는 이미 `omm install --force`도 하고 있어서 두 명령이
의미상 겹친다.

한편 사용자가 실제로 궁금해할 질문은 따로 있다: "지금 깐 모델보다 더 나은 게 나왔나?" 이 질문에
답하는 쪽으로 `upgrade`의 의미를 바꾼다. CLAUDE.md 원칙(브루/apt 느낌 유지, 명령 통합 시 옛
동작은 완전히 삭제하고 백워드 호환 별칭을 남기지 않음)에 따라 옛 동작은 알맞은 자리로 흡수하고
`upgrade`에서는 지운다.

## 목표

- `omm install --force`가 "원격이 이미 같으면 재다운로드 스킵"까지 하도록 만들어, 지금
  `upgrade`가 하는 같은-파일 재검증 기능을 완전히 흡수한다.
- `omm upgrade [MODEL]`을 "설치된 모델보다 하드웨어에 더 잘 맞는/더 나은 대안이 있는지 찾아
  제안하고, 승인하면 그 자리에서 설치까지 진행"하는 명령으로 바꾼다.
- 탐색은 두 갈래:
  - (A) 같은 HuggingFace/ModelScope repo 안에서, 메모리 예산 안에 들면서 지금보다 quant_bits가
    더 높은 형제 파일이 있는지.
  - (B) `published/candidates.json`에 수동으로 적어 둔 `supersedes` 계보를 따라, 지금 설치된
    모델을 대체하는 후속 큐레이션 모델이 있는지.

## 비목표

- 모델 계열/버전을 이름·repo_id 문자열 패턴으로 자동 추론하지 않는다. 오탐(잘못된 "업그레이드"
  추천) 위험이 크다고 판단해 기각했다 — 계보는 (B)의 수동 `supersedes` 필드로만 얻는다.
- HF 모델 카드의 `base_model` 태그를 런타임 조회하지 않는다. 태그가 없는 GGUF 양자화 레포가
  많고, 조회 자체가 매 실행마다 네트워크 비용을 늘린다.
- `candidates.json` 밖의(즉 `omm search`로 임의 설치한) 모델에 대해서는 (B)를 적용하지 않는다.
  일치하는 항목이 없으면 조용히 스킵한다.
- 큐레이션 후보 목록 자체를 늘리거나 큐레이션 프로세스를 바꾸는 일은 이 스펙 범위 밖이다.
- 다운그레이드 제안(더 낮은 quant로 속도를 얻는 케이스)은 다루지 않는다. "upgrade"라는 이름에
  맞게 품질이 오르는 방향만 다룬다.

## 설계

### 1. `install --force`로 흡수되는 부분

`_update_one`(`cli.py:6384`)의 로직 — HF repo 설치본은 `remote_file_sha256`으로 원격을 먼저
싸게 확인하고 다르면만 내려받으며, 직접 URL 설치본은 원격에 해시 엔드포인트가 없어 임시
파일로 받아본 뒤 해시를 비교한다 — 을 `install`의 강제 재설치 경로로 옮긴다.

옮긴 뒤 `install --force`의 동작:

1. 이미 설치돼 있고 `--force`가 켜졌으면, 다운로드를 시작하기 전에 위 방식으로 원격과 설치본이
   같은지 먼저 확인한다.
2. 같으면 "이미 최신본이다"라고 안내하고 재다운로드를 스킵한다 (지금처럼 무조건 전체
   재다운로드하지 않는다 — 안 바뀐 20GB 파일을 매번 다시 받는 낭비 제거).
3. 다르면 원래 `--force` 동작대로 새로 받아 교체한다.

`_update_one`, `upgrade` 커맨드의 `dry_run`/`all` 루프, `_prune_missing_models`와 얽힌 옛 배치
루프는 이 이관과 함께 삭제한다. 옛 `upgrade`가 쓰던 "N개 모델 업데이트 확인?" 같은 문구,
`up_to_date`/`updated`/`skipped` 카운트 요약도 함께 사라진다 — 그 요약은 새 `upgrade`의 "제안
탐색" 의미에는 안 맞는다.

### 2. 새 `omm upgrade [MODEL]`

시그니처는 유지한다: 인자 없음 또는 `all` → 설치된 모델 전체, 특정 모델명 → 그 하나만.
`--dry-run` 플래그도 유지하되 의미를 바꾼다 (아래 UX 절 참고). 별칭 `up`은 그대로 둔다.

#### 2-A. 같은 repo 안의 더 나은 양자화

대상 모델의 레지스트리 엔트리에서 `repo_id`, `provider`(`huggingface`/`modelscope`)를 읽는다.
`repo_id`가 없는 설치본(직접 URL 설치)은 이 체크를 스킵한다 — 비교할 "형제 파일"이라는 개념
자체가 없다.

1. 해당 provider의 `fetch_repo_files(repo_id)`로 그 repo의 `.gguf` 파일 목록을 받는다
   (huggingface.py:23, modelscope.py:85 — 이미 둘 다 있음, 추가 provider 작업 없음).
2. 지금 설치된 파일 자신은 후보에서 제외한다.
3. 남은 각 파일에 대해:
   - `featurize.parse_quant_bits(filename)`으로 quant_bits를 얻는다. `None`이면(양자화 표기를
     못 읽는 파일명) 그 후보는 스킵한다.
   - `remote_file_size(provider, repo_id, filename)`으로 바이트 크기를 얻는다.
   - `{repo_id, filename, size_bytes}` 형태의 candidate dict를 만들어
     `predictor.build_prediction_features` → `predict_speed`로 예측 tok/s를 계산한다.
   - `fit_ui.verdict`로 이 하드웨어의 메모리 예산 안에 드는지 확인한다. 예산을 넘으면 후보에서
     제외한다.
4. 예산 안에 남은 후보 중 지금 설치된 파일보다 quant_bits가 **더 높은** 것만 추린다.
5. 그중 quant_bits가 가장 높은 것을 추천 후보로 고른다. 동률이면 예측 tok/s가 더 높은 쪽,
   그것도 동률이면 파일 크기가 더 작은 쪽을 고른다 (디스크 절약).
6. 판정 기준은 **메모리 예산 통과 + quant_bits 상승**뿐이다. 예측 속도는 결과 화면에 참고
   정보로 같이 보여주지만 판정에는 안 쓴다 — 속도가 다소 떨어져도 품질이 오르는 게 이 기능의
   동기이기 때문이다.

#### 2-B. 후속 모델로 교체 (계보)

`published/candidates.json`의 각 항목에 새 선택 필드 `supersedes: list[str]`를 추가한다
(값은 그 항목이 대체하는 옛 항목들의 `name` 슬러그). 예:

```json
{
  "name": "llama3.3-8b-instruct-q4",
  "repo_id": "bartowski/Meta-Llama-3.3-8B-Instruct-GGUF",
  "filename": "Meta-Llama-3.3-8B-Instruct-Q4_K_M.gguf",
  "description": "Curated default",
  "provider": "huggingface",
  "supersedes": ["llama3.1-8b-instruct-q4"]
}
```

방향은 "새 항목이 옛 것을 가리킨다"로 고정한다 (`superseded_by`를 옛 항목에 다는 방식이
아니다) — 신규 후보를 큐레이션해 넣는 시점에 그 자리에서만 적으면 되고, 이미 있는 옛 항목을
소급 편집할 필요가 없다.

이 필드는 순수 수동이며 값을 채울지 말지도 큐레이터 재량이다. 자동 검증/린트는 v1에서
추가하지 않는다 — 팀이 자주 빼먹으면 그때 체크리스트나 CI 경고를 추가한다.

매칭 절차:

1. 설치된 모델의 `(repo_id, filename)`과 정확히 일치하는 candidates.json 항목을 찾는다.
2. 없으면(큐레이션 목록 밖에서 설치한 모델) 이 체크를 조용히 스킵한다. 실패해도 "몰라서 못
   찾음"이지 오탐이 아니므로 안전한 실패 모드다.
3. 있으면, 그 항목의 `name`을 자신의 `supersedes` 목록에 담고 있는 다른 항목을 찾는다.
4. 여럿이면(같은 옛 모델을 여러 후속작이 각각 계승 주장하는 경우) candidates.json에 먼저
   등장하는 순서대로 첫 번째를 쓴다 — 이런 충돌은 큐레이션 실수로 보고, 발생 시 후속 PR에서
   candidates.json 자체를 정리한다.

#### 두 갈래가 동시에 걸릴 때

(B)를 우선 제시한다. 완전히 다른/더 발전한 모델 자체가 같은 모델의 양자화 미세조정보다
임팩트가 크다고 보기 때문이다. (A)는 (B) 제안을 보여준 뒤 "그 외에 같은 repo 안에서 Q6_K도
가능함" 정도로 부가 정보로만 언급한다.

### 3. UX / 실행 흐름

```
$ omm upgrade                     # 설치된 모델 전체 스캔
$ omm upgrade llama3.1-8b-q4      # 특정 모델만
$ omm upgrade --dry-run           # 제안만 출력, 설치/확인 없음
```

흐름:

1. 대상 모델(들)에 대해 (B) → (A) 순으로 네트워크 조회를 포함한 스캔을 **먼저 전부 끝낸다**.
   이 단계는 순수 읽기이며 아무것도 설치하지 않는다.
2. 스캔이 끝나면 발견된 제안을 표로 한 번에 보여준다: 모델명 / 제안 종류(B: 후속 모델, A: 같은
   repo 상위 양자화) / 근거(예: "Q4_K_M → Q6_K, 예산 안에 듦" 또는 "후속 모델
   llama3.3-8b-instruct-q4 있음").
3. `--dry-run`이면 여기서 종료.
4. 아니면 표에 나온 순서대로 각 제안마다 개별적으로 `[y/N]`을 물어 승인된 것만
   `_install_impl`을 호출해 그 자리에서 설치한다. (한 번에 몰아서 "N개 다 설치할까요?"로
   묻지 않는다 — 제안마다 크기/트레이드오프가 다를 수 있어 개별 판단이 맞다고 봤다.)
5. 제안이 하나도 없으면 "N개 모델 확인함, 더 나은 대안 없음" 한 줄로 끝낸다.

먼저 스캔을 끝내고 나중에 개별 확인하는 순서를 고른 이유: 네트워크 조회 중간에 확인 프롬프트가
끼어들면 무엇을 상대로 예/아니오를 답하는지 맥락이 끊긴다. 표를 먼저 다 보여주면 사용자가
전체 그림을 보고 하나씩 판단할 수 있다.

(A)의 형제 파일 조회는 설치된 모델 하나당 provider API 호출이 최소 1회(`fetch_repo_files`) +
후보 파일당 1회(`remote_file_size`) 필요하다. `all` 모드에서 설치 모델이 많으면 호출 수가
그만큼 늘어난다. v1에서는 별도 캐싱/동시성 제한 없이 순차 호출한다 — 보통 설치 모델 수가
적어(수 개~수십 개) 문제가 안 될 거라 보고, 체감상 느려지면 후속 이슈로 병렬화를 검토한다.

### 4. 에러 처리

- provider API 호출 실패(네트워크 오류, repo 404/410 등): 그 모델의 (A) 체크만 건너뛰고
  "확인 못 함" 한 줄 남긴 뒤 나머지 모델/체크는 계속 진행한다 (지금 `upgrade all` 루프가
  한 모델의 예외를 잡아 배치 전체를 안 죽이는 것과 같은 원칙 — `cli.py:6738` 부근의
  try/except 패턴 유지).
- `candidates.json` 로드 실패(서명 검증 실패 등, `catalog.py:verify_signed_artifact`가 이미
  담당): (B) 체크 전체를 스킵하고 (A)만 진행. 기존 `recommend`/`search`가 이 실패를 다루는
  방식과 동일하게 처리한다(새 에러 처리 경로를 만들지 않는다).
- 설치 단계(4단계) 실패는 기존 `install` 커맨드의 에러 처리(`DownloadError`, `LinkError`,
  `InstallInterrupted`)를 그대로 재사용한다. `upgrade`가 그 위에 새 에러 타입을 얹지 않는다.

### 5. 테스트 계획

- `install --force`의 "원격 동일하면 스킵" 분기: HF repo 설치본/직접 URL 설치본 각각 원격이
  같을 때/다를 때 유닛 테스트.
- (A) 판정 로직: `fetch_repo_files`/`remote_file_size`를 mock해서 — 예산 밖 후보 제외됨, 더
  낮은 quant_bits 후보는 추천 안 됨, 동률 타이브레이크(속도 → 크기) 동작 확인.
- (B) 매칭 로직: candidates.json fixture로 — 정확 매칭 성공/실패, `supersedes` 다중 충돌 시
  첫 번째 선택, repo_id 없는(직접 URL) 설치본은 (A)만 스킵되고 (B)는 정상 동작.
- CLI 통합 테스트(네트워크 mock): 제안 있음/없음, `--dry-run`, `all` 모드에서 여러 모델 중
  일부만 제안 있는 경우, 하나는 승인·하나는 거절하는 혼합 케이스.

## 마이그레이션 / 하위 호환

- 이것은 breaking 변경이다: 스크립트로 `omm upgrade`를 "같은 파일 재검증" 용도로 쓰고 있었다면
  동작이 바뀐다. 백워드 호환 플래그(`--refresh` 등)는 만들지 않는다 (CLAUDE.md 원칙).
- `CHANGELOG`/릴리스 노트에 이 변경을 명시한다: "`omm upgrade`가 이제 대안 탐색을 한다. 같은
  파일 재검증이 필요하면 `omm install --force`를 쓴다."
- `published/candidates.json`의 스키마 변경(선택 필드 `supersedes` 추가)은 하위 호환이다 —
  기존 소비자(`predictor.py`, `search.py`)는 모르는 필드를 무시하므로 별도 마이그레이션 불필요.
