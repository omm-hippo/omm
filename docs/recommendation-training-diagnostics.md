# 추천 학습이 나빠졌을 때 확인할 것

측정 결과가 더 쌓였다고 추천 모델을 무조건 교체하지 않는다. 새 모델을 따로 둔
검증 데이터로 확인하고, 기존 품질 기준을 통과해야 게시한다. 이번 변경은 그 기준을
낮추지 않는다.

## 확인한 학습 구조 문제

기존 코드는 후보 모델을 검증한 뒤, 검증용 데이터까지 포함해 다시 학습한 별도
모델을 내보냈다. 따라서 게시된 나무들이 실제로 검증한 나무들과 달랐고, 그 모델은
다음 비교에서 검증 데이터 일부를 이미 학습했을 가능성이 있었다.

이제 통과한 후보의 나무들을 그대로 게시한다. 실제 학습·검증 구성의 해시도 기록해
이후 비교에서 중복을 확인할 수 있게 한다. 과거 모델에는 이 기록이 없으므로
과거 학습 데이터와 현재 검증 데이터가 겹쳤는지는 `unknown`으로 보고한다.
이 구조 문제가 최근 악화의 유일한 원인이었다고 단정하지 않는다.

## 2026-09-16 읽기 전용 스냅샷 분석

공개 Firebase 데이터에 읽기 요청 한 번만 보내 스냅샷을 확보했다. 원본 레코드는
이 저장소에 포함하지 않는다. 스냅샷 SHA-256:
`4343709f7690fbbe64d4d9b4497e3fb1b072e8daf27be8b0342499c67a1178d7`.

- 원본 664건 중 속도 학습에 사용할 수 있는 측정은 443건이었다. 같은 구성의
  반복 측정을 묶으면 320가지 구성이다. 그중 학습 243개, 검증 77개로 나눴다.
- 실제 속도 학습과 검증 데이터는 모두 Ollama였다. LM Studio까지 같은 수준으로
  잘 예측한다고 주장할 근거는 없다.
- 실행 불가로 확인된 예시는 1개뿐이었다. 적합/부적합 검사를 충분한 근거로
  판단하기 위해 요구하는 최소 5개에 못 미쳤다. 일부러 위험한 로드를 강행해
  실패를 만들지 않고, 정상적인 보호 절차에서 확인된 실패만 추가해야 한다.
- 검증 데이터에서 RAM 약 16 GiB / VRAM 6 GiB인 그룹의 평균 절대 오차가
  기존 모델보다 약 11.23 tok/s 커졌다. 이 그룹은 9개 구성이라 결과를 모든
  16 GiB 기기로 일반화하면 안 된다.
- 모델 크기별로는 3B 미만에서 오차 증가가 더 컸다. 이 구간 41개 검증 구성의
  평균 절대 오차는 기존보다 약 3.84 tok/s 증가했다.
- 순위를 비교한 하드웨어 그룹은 3개였고, 각 그룹에 2~4종류의 실행 설정이 섞였다.
  같은 기기에서 같은 문맥·배치·스레드 설정으로 여러 모델을 비교한 자료를
  늘려 설정 차이와 모델 차이를 구분하는 것이 다음 수집 우선순위다.
- 기존 모델의 1순위 선택 지표는 0.667, 새 후보는 0.167이었다. 이 결과는 이
  검증 세트의 수치이며 모든 사용자에 대한 정확도가 아니다. 기존 모델을 유지했다.

9월 15일 작업이 읽은 640건과 이번 664건은 서로 다른 시점의 데이터다. 이번
실험은 최신 스냅샷에서도 악화가 재현됨을 확인한 것이며 과거 입력을 복원한 것은 아니다.

## 반복해서 분석하기

```sh
python scripts/train_model.py --offline \
  --telemetry-file /path/to/local-telemetry-snapshot.json \
  --quality-gate --minimum-real-configurations 100 \
  --baseline published/localfit-recommend-model.json \
  --output /tmp/recommendation-candidate.json \
  --quality-report /tmp/recommendation-quality.json \
  --diagnostics-report /tmp/recommendation-diagnostics.json
```

진단 보고서는 엔진·메모리·모델 크기·양자화별 오차, 부족한 측정 근거와 추가
수집 우선순위를 담는다. 학습 데이터 자체의 점수는 `in_sample_diagnostics_not_validation`
으로 표시해 검증 성능과 구분한다. 데이터가 부족해 학습을 건너뛰어도 이유를 남긴다.
자동 학습에서는 보고서를 `recommendation-regression-diagnostics` 산출물로 보관한다.

이 보고서는 수집 방향을 알려준다. 사용자의 기여 작업을 원격으로 실행하거나,
새 측정치를 만들어 내거나, 품질 기준을 완화하거나, 탈락한 후보를 배포하지 않는다.

## 측정 자료의 범위와 수집 우선순위

`scripts/benchmark_coverage.py --telemetry-file SNAPSHOT --output REPORT.json
--markdown REPORT.md`는 네트워크 요청이나 학습 없이 로컬 자료의 범위를 집계한다.
메모리 유형, 인코딩된 CPU/GPU 프로필, 실행기, 양자화 비트, 문맥 길이별 구성을
보여준다. 학습 진단의 `observed_coverage`에도 같은 집계가 들어간다.

원시 행 수, 반복 측정을 묶은 구성 수, 학습 구성과 검증 구성, 합성 사전 자료를
구별한다. 현재 벤치마크 스키마에는 인증된 장비 식별 정보가 없으므로 독립 장비 수는
`null`이다. 비슷한 특성으로 인코딩된 하드웨어 프로필을 실제 장비 수로 해석하지 않는다.
검증 자료가 없는 조건과 관측 구성이 적은 조건을 추가 수집 대상으로 표시한다.
검증 오차는 기존 `slices`에서 확인하며, 검증 행이 존재한다는 것만으로 신뢰도를
주장하지 않는다.

## 반복 속도 관측의 영향 제한

같은 구성의 속도가 반복 제출될 때 기존 단순 중앙값은 제출 횟수에 영향을 받는다.
이제 같은 구성 안에서 최솟값의 5% 범위에 드는 속도를 하나의 관측 묶음으로 만들고,
각 묶음의 중앙값을 동일한 비중으로 집계한다. 인접한 값끼리 연쇄로 묶지 않으므로
작은 변화가 이어져도 서로 먼 속도가 한 묶음이 되지 않는다.

5%는 반복·근접 제출의 영향 제한에 쓰는 규칙이며 검증된 신뢰구간이 아니다.
느린 값이나 드문 구성은 이 단계에서 삭제하지 않는다. 모든 원시 행은 기존 감사
집계에 남고 `repetition_balance`에 줄어든 반복 비중과 관측 묶음 수를 기록한다.
서로 다른 속도 묶음이나 구성을 대량 위조하는 공격, 제출자의 진실성, 독립 장비 수는
이 규칙으로 확인하지 못한다. 물리 상한, 이상치 정책, 데이터·예측 품질 게이트는
그대로 유지하며 기준을 통과하지 못한 학습 모델은 게시하지 않는다.

## 다른 장비에서 측정할 때

장비 소유자가 측정과 자료 공유 범위를 먼저 선택한다. 이미 설치된 모델 두 개 이상을
같은 문맥 길이·스레드·오프로드·배치 설정으로 비교하고, OMM과 실행기 버전도
기록한다. 업로드 동의와 측정 동의는 구별하며 업로드를 자동으로 활성화하지 않는다.

```sh
omm --version
omm engine status --json
omm info MODEL --json
omm benchmark MODEL --speed-runs 3 --output local-benchmark-evidence.json
```

`MODEL`은 해당 실행기에 이미 설치된 모델의 정확한 식별자로 바꾼다. 마지막 명령은
실제 모델을 로드해 측정하므로 소유자가 확인한 경우에만 실행한다. 사용 중인 앱을
강제로 종료하거나 무기한 기여 루프를 시작하지 않는다. 업로드 질문에서 거절한
결정은 그대로 유지한다. 증거 파일과 집계용 벤치마크 레코드의 형식은 다르므로
형식을 확인하고, 기록에 없는 CPU 특성이나 실행 설정을 임의로 보충하지 않는다.
